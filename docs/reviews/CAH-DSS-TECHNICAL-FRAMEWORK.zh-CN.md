# 让 AI 持续完成工作：CAH / DSS 的技术框架与工程实践

### 从持久任务、多智能体接力，到可恢复执行与跨宿主迁移

> **摘要**
>
> 当 AI 从回答问题走向承担工程、研究和创作任务，系统需要解决的问题也随之变化：工作怎样跨越会话边界，成果怎样被后继执行者继承，遇到中断怎样恢复，原有方案失效后怎样重新选择路线。
>
> [Chat Agent Harness（CAH）](https://github.com/Tests4gptplay/chat-agent-harness) 与 [DeepSeek Servant（DSS）](https://github.com/Tests4gptplay/deepseek-servant) 围绕这些问题形成了一条持续演进的技术路线：以持久任务为中心，将模型推理、角色协作、工作记忆、状态调度与执行环境分离。CAH 提供了长期任务和技术路线调整的实际案例，DSS 则将同一架构原则迁移到 DeepSeek Harness 的原生 Agent 环境。
>
> 两者共同探索的是：**让执行者可以更换、工作方法可以调整，而用户目标、已有成果和后续责任保持连续。**[^project-review]

**关键词：** Agent Harness · 持久任务 · 多智能体协作 · 生命周期管理 · 状态驱动 · 中断恢复 · 跨宿主迁移

## 一、从“完成一次回答”到“承担一项工作”

设想这样一项任务：分析一批实验数据，定位异常，修改处理程序，运行新的计算，比较结果，最后交付图表、说明和可复现脚本。

它可能持续数小时甚至数天。期间，用户会补充要求，工具会返回意外结果，部分方案需要推翻，模型上下文和执行进程也可能发生变化。

对于这类任务，单次回答质量只是其中一个环节。系统还需要持续回答几个问题：

**现在到底在完成什么？哪些事情已经验证？哪些尝试失败过？已有成果在哪里？接下来应该继续执行，还是重新规划？**

Anthropic 在长期 Agent 工程研究中，将这一问题形容为多个工程师轮班工作：每次新的会话都需要重新理解工作现场。如果缺少明确的进度记录和可接手的工程状态，后继就容易重复调查、误判完成，或者在半成品基础上继续扩大问题。其解决方向包括增量执行、持久进度、Git 历史和实际功能验证。（[Anthropic：Effective Harnesses for Long-Running Agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）

CAH/DSS 的出发点与这一问题直接相关：

> **让任务的持续性由系统维护，让模型专注于当前需要完成的判断与行动。**

这里可以区分三个层次：

| 层次 | 主要职责 | 典型对象 |
|---|---|---|
| **模型能力** | 理解、推理、规划、生成和评价 | 大语言模型 |
| **执行宿主** | 提供会话、工具、文件、作业和运行环境 | ChatGPT 执行入口、DSH、浏览器、本地程序 |
| **任务组织架构** | 保存目标与进度，安排协作、接力、恢复和验收 | CAH/DSS 的持久任务与生命周期机制 |

这一划分使系统可以分别演进：模型能力提升时可以使用更强的执行者；工具环境变化时可以调整适配；长期任务及其已有成果则继续保留。

## 二、CAH 与 DSS：同一套架构的两种实现

**CAH 是原始架构和长期运行实践，DSS 是这套架构在另一种宿主环境中的原生实现与扩展。**

CAH 将 ChatGPT 会话、Git 持久记录和本地执行工具连接起来。任务的目标、进展与交接依据保存于会话之外，模型会话则作为可以替换的推理与执行上下文。

DSS 延续这一原则，使用 DeepSeek Harness（DSH）的原生 Agent、Session、工具和 Jobs 承载工作，并发展持续前台、Local／Git 两种持久化方式，以及进一步的任务组织与归档能力。[^cah-scheduler][^dss-acceptance]

| 比较维度 | CAH | DSS |
|---|---|---|
| **模型与会话入口** | ChatGPT 会话及相关执行通路 | DSH 原生 Agent／Session |
| **任务组织** | Task Cell、父子任务、Planner／Worker 协作 | 继承同一任务组织原则，扩展目标组织与持续交互 |
| **持久工作资料** | Git 中的任务、记忆、工作记录及成果引用 | Local／Git 模式下的任务与工作资料 |
| **执行环境** | 本地 Runner、脚本、浏览器和专业软件 | DSH 原生工具、Jobs 和工作区 |
| **持续性机制** | 会话接替、工作交接、恢复与阶段验收 | 原生会话生命周期下的接续、恢复与交付 |
| **共同核心** | **任务长期存在，执行者可以替换，成果与判断可以继承** | **相同核心在另一套宿主中落实** |

CAH 已经具备任务树。Task Cell 提供任务的管理与运行边界，父任务和子任务表达工作关系，Planner、Worker、Helper 则围绕这些任务承担不同职责。DSS 的发展，是继续扩展这一体系的组织范围和宿主接入方式。[^cah-scheduler]

这使两项工程具有相互补充的意义：**CAH 回答这套机制能否承担真实长任务，DSS 回答它能否离开最初的宿主继续成立。**

## 三、技术框架：围绕持久任务组织可替换的执行者

### 3.1 整体职责框架

下面是 CAH/DSS 的高层职责示意。各角色按任务需要参与；DSS 的 Organizer、Recorder 属于这条架构的扩展设计。

```text
用户
目标、约束、反馈、暂停与继续
                 ↕
┌─────────────────────────────────────────┐
│ Foreground：持续交互与任务入口          │
│ 理解要求、传递反馈、核对并交付成果      │
└─────────────────────────────────────────┘
                 ↕
┌─────────────────────────────────────────┐
│ 持久任务组织                            │
│                                         │
│ 总目标 → 子任务 → 阶段成果 → 验收       │
│                                         │
│ Planner：规划、分派、评审与改策         │
│ Worker：执行、验证、记录与接力          │
│ Helper：按故障介入诊断与恢复            │
│                                         │
│ DSS 扩展：                              │
│ Organizer：组织多个独立目标             │
│ Recorder：整理长期记录与经验            │
└─────────────────────────────────────────┘
          ↕ 工作事实、成果与状态
┌─────────────────────────────────────────┐
│ 持久工作资料                            │
│ 任务要求 · 当前计划 · 决策与证据        │
│ 工作记录 · 工程成果 · 可复用经验        │
└─────────────────────────────────────────┘
                 ↕
┌─────────────────────────────────────────┐
│ Host / Runtime：状态驱动的运行协调      │
│ 发现待办、安排执行、观察与生命周期管理  │
└─────────────────────────────────────────┘
                 ↕
┌─────────────────────────────────────────┐
│ 模型与工具执行环境                      │
│ CAH：ChatGPT / Git / 本地工具           │
│ DSS：DSH Agent / Session / Jobs         │
└─────────────────────────────────────────┘
```

CAH 的契约将语义角色与确定性运行职责分开；DSS 总纲则进一步明确了前台、规划、执行、组织、恢复、归档及 Host 的职责。共同原则是：**AI 理解工作并决定业务方向，运行系统根据持久状态兑现执行安排。**[^cah-contract][^dss-design]

### 3.2 任务、计划、记忆和成果分别承担什么作用

一项长期任务需要保存的内容，不只是聊天历史。

**任务要求**保存用户想得到的结果、约束和验收条件；**计划**保存当前采用的路线及后续步骤；**工作记忆**保存重要决策、已经验证的事实、失败尝试和未解决问题；**工程成果**则是实际生成的代码、数据、文件、构建结果或媒体作品。

这些对象分开之后，系统可以保留用户目标，同时调整计划；也可以更换执行会话，同时继承已经完成的成果。

例如，执行者发现当前加载方案不可行，应当更新方案与证据，而不是把用户原本的目标一起改掉。新的 Worker 接手时，需要知道哪些结论已经成立、哪些仍是待验证假设，以及从哪个位置继续工作。CAH 的工作接续和 DSS 的记忆设计，都围绕这类信息组织。[^cah-scheduler][^dss-design]

从使用方式理解，**当前上下文是执行者的工作现场，持久任务资料和工程成果是项目的长期资产。**

### 3.3 状态驱动调度怎样实现解耦

在 CAH/DSS 中，任务事实、待处理通知和执行实例各有职责。

任务状态表达工作已经推进到哪里；通知表达有一项工作需要某个角色接手；执行实例则是当前承担这项工作的具体会话或进程。消费通知之后，任务事实和成果仍然存在。[^dss-design]

这一分离有几个直接效果：

| 解耦关系 | 实际作用 |
|---|---|
| **任务与会话分离** | 更换会话后仍然可以继续原工作 |
| **工作事实与通知分离** | 一次通知处理结束，不会抹掉任务进展 |
| **业务判断与运行调度分离** | 模型负责理解与选择，Host 负责运行安排 |
| **业务交接与执行退出分离** | 已保存的交接继续有效，旧执行的收尾独立处理 |
| **成果验收与运行维护分离** | 已接受成果保留，故障处理针对对应执行问题 |

CAH 的原始契约已经明确：角色把成果和工作事实写入持久记录后，由 Harness 读取对应结果推进；已经接受的语义工作不会因为后续物理清理失败而被撤销。[^cah-contract]

因此，解耦并不是后来附加的优化，而是这套架构组织长期任务的基础。

## 四、运作机制：怎样从用户目标推进到完整交付

一次典型的长期任务，可以概括为：

**明确目标 → 建立任务 → 分解工作 → 执行与验证 → 保存进展 → 接力或重新规划 → 验收交付 → 整理经验。**

其中有三条相互配合的循环。

### 第一条：执行循环

Worker 读取当前工作要求和必要资料，使用工具处理实际问题，检查结果，再把有用的进展保存下来。

执行结果可以是代码修改、计算结果、文件输出，也可以是明确的失败证据。后续决策使用这些事实继续推进。

这一过程与 ReAct 所研究的“推理—行动—观察”结合有直接联系：模型通过行动获取环境反馈，再据此调整下一步判断。CAH/DSS 将这样的局部执行循环放进更长的任务生命周期中。（[ReAct 论文](https://arxiv.org/abs/2210.03629)）

### 第二条：协作与评审循环

当工作可以独立拆分时，多个 Worker 可以并行处理不同部分；当一个工作段需要新的执行上下文时，由后继继续；到达需要判断方向或质量的节点时，Planner 根据成果进行评审。

这里包含三种不同的协作收益：

| 协作方式 | 主要用途 |
|---|---|
| **横向并行** | 同时推进相对独立的工作部分 |
| **纵向接力** | 在上下文或执行生命周期变化后继续同一项工作 |
| **阶段评审** | 重新检查当前方法、实际成果与整体目标是否一致 |

CAH 的调度协议分别定义了持续执行、Worker 换代、Planner 中间评审和完成验收。前台也保留直接处理短小任务的路径，使任务组织方式与实际工作规模相匹配。[^cah-scheduler][^cah-foreground]

### 第三条：中断与恢复循环

发生中断时，系统需要辨认尚未完成的责任，并根据已经保存的资料恢复执行。

恢复的对象可能是一个 Worker、Planner 的某轮工作，也可能是宿主运行环境。已经完成的成果继续保留，后继从明确的工作位置接续。

用户在此期间仍然可以补充要求、调整方向、暂停或继续任务。前台将这些变化关联到对应工作，使业务协作与后台执行保持连接。[^cah-foreground]

**长期任务的连续性，正是由这三条循环共同形成的：持续执行、重新判断，以及恢复后继续。**

## 五、工程案例：持续完成与有效改路

### 5.1 多日媒体制作：同一任务跨越中断走到验收

CAH 的一项媒体制作任务从 **2026年10月17日**启动，到 **10月22日**完成 Planner 初稿验收，完整任务周期约 **4天11小时**。期间包含执行接替、运行恢复和用户改策，最终形成 **211.9 秒、30 fps 的完整 MV 初稿**，并留存源工程与重建验证材料。[^project-review][^mv-records]

这个案例体现的，是任务层面的持续性：运行条件发生变化后，原任务、既有工作和后续要求仍然能够关联起来，最终推进到明确的成果验收。

**中断恢复应当被视为长期执行能力的一部分。** 真实工作本来就包含等待、维护、反馈与方案调整。值得考察的是这些事件之后，工作还能否继续、需要补充多少上下文，以及会损失或重做多少内容。

### 5.2 Viewer：有效成果被继承，技术路线被重新选择

2026年9月28日的 Viewer/Cook 任务，先分别推进资源构建与 Viewer 基础，再进行集成。任务从新的工程基线出发，将历史实现作为参考，在实际加载与画面检查中重新选择运行方式。

最终方案从历史 Editor 托管路线转向独立打包的 Game runtime，并调整加载和打包策略。有效外部资源得到保留，任务在 **5小时1分30秒**后通过原生画面和交互验收。[^viewer]

这一案例包含几个值得注意的行为：

| 已观察到的行为 | 对长期 Agent 的意义 |
|---|---|
| 历史方案作为参考，重新判断当前环境 | 经验能够复用，同时保持方案选择空间 |
| 构建或接口成功后，继续检查实际画面 | 验收持续对应用户需要的结果 |
| 当前路线受阻后调整实现方式 | 围绕目标重新寻找有效解法 |
| 改路时保留已有有效输入和成果 | 重新规划可以建立在前序工作之上 |

Viewer 的意义不仅是任务完成，还在于它展示了**保持目标、继承成果与改变方法可以同时发生**。

有生命周期的接力和阶段评审，为后继重新阅读任务、检查证据和质疑当前方案提供了明确位置。Viewer 已经呈现了这种组织方式下的成功纠偏；进一步实验可以分析不同轮动与评审策略对改路效率的影响。

### 5.3 DSS 原生运行：同一机制进入新的宿主

DSS 的原生验收覆盖了两代 Worker 接力、真实文件与 Jobs 执行、Planner 验收，以及实际宿主进程终止后的任务恢复。

该轮测试使用实际 DSH Agent、Session、文件工具、Jobs 和存储服务，模型响应与 Git API 使用受控对端。进程恢复后，系统读取已有文件，保留前段成果，继续后续工作，最终完成结果核对与交付。[^dss-acceptance]

三组案例放在一起，形成了不同层面的证据：

| 实践 | 主要体现 |
|---|---|
| **多日 MV** | 跨中断、跨执行接替的任务连续性 |
| **Viewer** | 长期执行中的技术路线重估与实际验收 |
| **DSS 原生运行** | 同一架构原则在另一种宿主中的实现与恢复 |

## 六、技术优势：让进展能够积累，让执行环境能够变化

### 6.1 保留成果，而不是反复重建上下文

长期任务中的成本，往往来自重复理解、重复试验和重新定位工作现场。

持久任务资料使后继可以找到已经验证的结论、失败尝试和实际产物，把精力集中到尚未完成的部分。工程经验因此能够跨越一次模型会话继续发挥作用。

这里的价值不只是“记得更多”，而是**知道哪些信息应当继续影响后续行动**。

### 6.2 在继承经验的同时，保留纠偏机会

长期推理可能逐渐被某个局部技术问题主导。对于工程任务，重要的是把“完成用户目标”与“坚持当前实现方法”区分开。

CAH 的持久目标、执行接力和阶段评审为重新判断提供了结构。Viewer 的案例说明，这样的组织能够承载实际改路过程：已有成果继续使用，具体方法根据证据调整。[^viewer]

**需要持续继承的是有效成果与可靠事实，工作假设则可以随着证据更新。**

### 6.3 跨宿主迁移，使架构价值独立于单一入口

CAH→DSS 的演进是一个重要检验：更换模型会话与工具宿主后，长期任务的组织原则仍然可以实现。

迁移时发生变化的是会话创建、工具调用、作业管理和存储接线；保留下来的是任务要求、角色职责、成果记录、接力与验收关系。DSS 的原生运行为这种迁移提供了实际依据。[^dss-acceptance]

因此，跨平台能力可以分层理解：**架构层复用工作组织方式，适配层处理宿主、操作系统和工具差异，具体环境通过相应运行测试确认。**

在这一基础上，CAH 与 DSS 的跨系统委派、成果回传和任务接续具有清晰的发展方向。不同执行端可以使用各自适合的模型和工具，围绕共同的任务要求协作。

### 6.4 工作积累由用户掌握

CAH 的 Git 记录，以及 DSS 的 Local／Git 工作资料，使任务过程和工程成果具有明确的保存位置。

这对需要长期维护的工程尤其重要：后续执行者、开发者或使用者能够检查已有记录，继续利用成果，也能够结合新的模型与工具调整执行方式。项目资料不必随着一次会话结束失去用途。[^cah-scheduler][^project-review]

Git 在这里提供版本历史和共享记录能力；任务树、角色生命周期与验收关系则赋予这些记录明确的工作语义。

## 七、同类型产品：共同面对持续协作问题

Grok Bot、Meta Muse 和 OpenAI dots 都已经将长期目标、记忆和后台行动组织为持续型助理产品。它们与 CAH/DSS 面对相近的问题，但在产品整合方式和工程关注点上各有侧重。

| 产品或实现 | 官方公开的主要方向 | 与 CAH/DSS 的技术联系 |
|---|---|---|
| **Grok Bot** | 持续工作的 Agent 团队，自有计算环境，跨工具和应用完成工作 | 多执行者分工、持续工作与任务交接。（[xAI 官方介绍](https://x.ai/news/introducing-grok-bot)） |
| **Meta Muse** | 围绕个人长期目标主动行动，保存记忆，使用专属虚拟执行环境 | 长期交互如何连接到目标管理和持续执行。（[Meta 官方介绍](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)） |
| **OpenAI dots** | 持续处理目标和工作，使用云端电脑与应用连接，在多轮交流之间推进任务 | 前台交互、后台工作和长期上下文的组织。（[OpenAI 官方介绍](https://openai.com/index/introducing-dots/)） |
| **DeepSeek 团队公开的 Super-agent 研究原型** | 接收 GitHub／飞书等事件，为工作项建立独立执行会话，并返回结果 | 持久工作项、执行实例和事件处理的分离。[^superagent] |

这些产品和研究实现说明，持续型 Agent 已经成为一个具有现实需求的方向。

CAH/DSS 的特点，在于把这一问题落实到**用户自己的工程环境、可检查的工作记录、明确的角色生命周期，以及不同宿主之间的架构复用**。对于需要专业工具链、持续项目资产和可追溯执行过程的使用者，这些属性具有直接价值。

研发时间也提供了背景：CAH 的早期设计记录形成于 **2026年9月17日**，**9月20日**已有公开发行；Muse 于 **9月8日**公开，dots 于 **9月29日**公开。CAH 属于这一轮持续型 Agent 产品化早期已经形成具体实现的独立路线。其技术分量则主要由后续任务成果和宿主迁移来体现。[^project-review]（[Meta 发布资料](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)；[OpenAI 发布资料](https://openai.com/index/introducing-dots/)）

## 八、相关论文与工程研究：这套工作处在什么技术脉络中

CAH/DSS 涉及的核心问题，能够与近年的 Agent 研究形成具体对应。

### 8.1 从局部行动到长期协作

| 论文或研究 | 核心问题 | 与 CAH/DSS 的对应关系 |
|---|---|---|
| **ReAct: Synergizing Reasoning and Acting in Language Models**，2022／ICLR 2023；arXiv:2210.03629 | 让推理、行动与环境反馈交替发生 | 对应 Worker 的实际执行与结果反馈循环。（[论文](https://arxiv.org/abs/2210.03629)） |
| **MemGPT: Towards LLMs as Operating Systems**，2023；arXiv:2310.08560 | 管理有限上下文与外部记忆之间的信息流 | 对应当前上下文与长期工作资料分离。（[论文](https://arxiv.org/abs/2310.08560)） |
| **Magentic-One: A Generalist Multi-Agent System for Solving Complex Tasks**，2024 | 由协调者维护任务与进度记录，在停滞时重新规划 | 对应任务分解、进度判断和阶段性改策。（[Microsoft Research](https://www.microsoft.com/en-us/research/articles/magentic-one-a-generalist-multi-agent-system-for-solving-complex-tasks/)） |
| **Why Do Multi-Agent LLM Systems Fail?**，2025；arXiv:2503.13657 | 分析系统设计、Agent 间协调、验证与终止方面的失败 | 对应职责边界、工作交接与成果验收问题。（[论文](https://arxiv.org/abs/2503.13657)） |
| **Towards a Science of Scaling Agent Systems**，2025起；arXiv:2512.08296 | 研究任务结构、协作组织与成本怎样共同影响表现 | 对应并行、接力和集中评审应怎样组合。（[论文](https://arxiv.org/abs/2512.08296)） |
| **The Agentic Scientist: Orchestrating Coding Agents for Automated Scientific (Co-)Discovery**，2026；arXiv:2610.18933 | 将研究拆成规划、实验、验证、汇总和分析等阶段，组织长期探索 | 对应长期目标、跨 Agent 组织、成果继承与路线重估。（[论文](https://arxiv.org/abs/2610.18933)） |

这些研究共同说明，Agent 效果不仅受到模型能力影响，也受到上下文组织、协作方式和验证机制影响。

对 CAH/DSS 而言，系统层贡献可以进一步聚焦为：**如何让这些能力在跨日、跨会话、跨运行条件的真实任务中保持一致，并形成可交付成果。**

### 8.2 三项直接相关的工程实践

**Anthropic 的长期 Agent harness。**  
其工作强调，新会话需要取得清晰的工程状态、进度和验证依据，才能持续进行增量开发。这与 CAH 的跨代工作接续直接相关。（[工程文章](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)）

**Anthropic 的 Managed Agents。**  
该设计将持久会话记录、模型执行循环和工具环境分离，使组件可以独立替换和恢复。这为 CAH/DSS 的任务状态与执行载体分离提供了直接技术参照。（[工程文章](https://www.anthropic.com/engineering/managed-agents)）

**Letta 的 Context Repositories。**  
其方案使用文件和 Git 管理长期记忆，使 Agent 能够借助常规工具读取、整理和版本化上下文。CAH/DSS 进一步将工作记录与任务身份、执行进展和验收关系结合起来。（[工程文章](https://www.letta.com/blog/context-repositories/)）

将这些工作放在一起，可以看到一条清晰的技术演进方向：

> **从模型内部的一次推理，走向由持久状态、可替换执行者、外部工具和验证过程共同构成的长期系统。**

CAH/DSS 的工程实践处在这条路径上，其研究对象是完整工作如何持续推进，而不只是某一次模型调用怎样获得更好的输出。

## 九、对企业研发有什么实际意义

企业中的许多任务天然具有长期性：软件维护、实验数据处理、仿真计算、资料整理、媒体制作、工具链集成，都需要多轮执行与反馈。

以实验数据处理为例，可以将一项工作组织为：数据检查、处理程序、计算运行、异常复核、结果比较和报告生成。相对独立的工作并行推进，涉及方法选择的节点集中判断；若计算环境重启，恢复后根据已有文件和记录继续；若结果暴露原假设有问题，则保留数据与有效步骤，调整方法再次验证。

这是 CAH/DSS 架构可以承载的一类应用方式。其预期收益主要来自**减少重复说明、保留有效进展、降低任务交接损耗，以及让技术调整围绕同一目标持续进行**。

| 工作场景 | 典型需求 | 适合关注的系统能力 |
|---|---|---|
| **软件与工具研发** | 多阶段实现、测试、返工和版本维护 | 工作接续、阶段验收、成果保留 |
| **实验与数据分析** | 长作业、异常复核、方法调整和结果复现 | 持久记录、恢复接续、证据驱动改策 |
| **三维与媒体制作** | 专业软件链、素材积累、效果检查 | 实际工具执行、视觉验收、路线转换 |
| **跨日项目协作** | 多个目标、人员反馈和长期进展 | 任务树、角色分工、状态与成果可追溯 |

在评估这类系统时，最有解释力的指标是实际完成质量、人工纠偏次数、重复劳动、恢复后的有效进展，以及总时间和调用成本。

协作策略也需要随任务调整。Agent scaling 研究表明，可并行任务和强顺序依赖任务对组织方式的需求不同。因此，系统设计的重点是让并行、接力与评审各自承担合适的工作，而不是单纯增加 Agent 数量。（[Google Research：Towards a Science of Scaling Agent Systems](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)）

## 十、结语：把模型能力积累为可持续的工作能力

CAH/DSS 的核心，可以归纳为四句话：

> **任务持续存在。**  
> **执行者可以替换。**  
> **方案可以根据证据调整。**  
> **同一组织方式可以迁移到不同宿主。**

CAH 的多日任务展示了跨中断的持续推进，Viewer 展示了继承成果后的技术改路，DSS 则通过原生运行验证了另一种宿主中的实现。这些证据共同构成了一项具体的系统工程实践。[^project-review][^viewer][^dss-acceptance]

其技术价值在于，将模型的推理和工具使用能力组织成一个有目标、有记录、有协作、有验收、能够恢复的工作过程。模型继续进步时，这套架构可以承载更强的执行者；宿主和工具变化时，任务的组织原则仍然具有复用空间。

**从一次回答到一项持续完成的工作，中间需要的是任务、记忆、执行和验证之间的系统性连接。CAH 与 DSS 所探索的，正是这部分连接怎样在真实工程中发挥作用。**
