## Actual original consumers

The frozen v44 source contains `LegacyTasks` in `client-page.tsx`: an explicit Resume button for paused imported tasks and an Answer form for the exact original pending question. The controller calls `FrameworkService.legacyControl`, which resolves an existing migration from `technical/legacy-migrations/index.json`, resolves this instance's registered member, and invokes `resumeLegacyTask` or `answerLegacyTask`. These are existing user actions, not permission to start another migration.

The preserved Foreground signal identifies a migration and its mapped Task. Foreground reads the original records and supplies an explicit P/O decision through `dss_submit_task({ legacyTask: { manifestPath, oldTaskId }, ... })`. The Host does not infer that decision from participant counts, child counts or task complexity. Existing admitted tasks keep their owner, source and route.

Both the frozen v44 package and the current source contain these manifest consumers but no manifest producer. The consumers address preserved `LEGACY_BASELINE` (0acd3ba39a2ae23d66759279b3c54c4637cd0ad5) records. The earlier delivered producer was verified separately, as recorded below. No particular user manifest was inspected or assumed to exist. These controls are distinct from the new once-only AI-guided SQLite-to-physical upgrade. That upgrade may preserve existing manifests but must not manufacture one for every old Task or resume held work automatically.

## Preservation constraints

- The original continuation, record references, plans, worker inputs/reports and pending questions remain available at their existing addresses.
- A resume or answer on an already admitted Task appends the actual user action to its current source and notifies its existing owning role. It must not restore old Plan, Worker or Inbox bytes over newer work.
- Before admission, missing original member material may be restored with create-if-absent operations. Existing files, including empty authored files, remain authoritative.
- Current Task and completed history identity must prevent accidental reopening. Other migration tasks and member summaries must survive same-manifest updates.
- Git retains its original transactional publication path. Physical Local does not claim a multi-file transaction, uses its explicit file-publication continuation rather than a generic transaction fallback. Ordinary Local now selects this physical backend.

Physical implementation follows the verified prior producer below. Existing non-Physical transactions remain unchanged. This note distinguishes source provenance and controlled checks from native acceptance. No native DSH, Windows or full TypeScript check has been completed for these ports.

## Physical publication order

`physical-legacy-publication.ts` serves only a selected, already-existing migration. The existing `controls/<hash>.json` identity retains the exact user action. The pending entry saves the accepted action before any original control or prepared file is created, so that an interruption cannot leave accepted input without its exact restart owner. Its temporary `physicalPending` property distinguishes incomplete publication from the historical successful representation. The exact `.Legacy_Control_*.json` or `.Legacy_Route_*.json` entry in the existing state directory lets the existing Host observation resume only that accepted operation. No migration enumeration, new confirmation, general FileChange publisher, permanent readiness flag or additional scanner is introduced.

Controls on an admitted Task use its current source and append the original action, then update only the selected summary inside the current shared manifest and publish its owning-role notification. Before admission, absent original member files are restored individually; existing files are not replaced. A route selected by Foreground prepares original input and absent defaults, then creates mapped metadata, exposes its source, updates the selected routing summary and publishes the ordinary role signal. Source discovery sees the existing mapped metadata. P Inbox preparation appends the preserved requirement without replacing an existing member input. O appends only the actual Foreground routing decision and exact original-file references to the existing Task Organizer_Note.md. It does not create a shared O or member Inbox responsibility, and leaves the old member Inbox unchanged. Before metadata becomes visible, the existing Recorder Cache gains exact file links to this mapped Task record, continuation and accepted control files. These links locate the actual originals; they do not create a separate read-permission test. Recorder may read another exact relevant reference within the existing storage scope without adding it to Cache.

Only the same mapped Task is coordinated with other legacy actions and its existing physical terminal lane. Different Tasks share only the actual manifest file's short read-modify-write. Successful controls return to their original plain action representation, and exact temporary pending/stage files retire. If a source or signal publication is interrupted, its prepared file identity or the existing receiver's accepted source confirms it. Missing stages alone do not cause a signal replay. Later control input finishes an accepted route first and then supplements its current Task, never restores stale work over it.

## Terminal ordering and retention

An accepted route holds the existing same-Task physical terminal lane while preparing necessary input and its exact Recorder references. If cancellation or completion occurs after metadata becomes visible, Recorder can already read the original requirement and actual routing decision. Resuming that route only clears its selected `routePending` summary and retires its exact pending/prepared files. It does not write a late source, recreate metadata, restore templates or emit P/O work, including when Cleaner finished first. No Cleaner waiting condition, new role, public Task status or permanent readiness marker is added.

An accepted resume/answer overtaken by an actual terminal decision keeps the exact original action in its original control file with `supersededBy` identifying the terminal disposition. It does not claim a new business delivery or notify the former owning role. Existing successful control identity and source publication evidence still close retries without replay.
